# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**The project is called Mailchilla; the GitHub repository is `vogster/3x-ui-mailchilla-bot`.** The names differ on purpose — the repository was renamed so that it turns up in searches for 3x-ui, while the product keeps its own name in `APP_NAME`, the panel, the letters and both READMEs. Do not "correct" either one to match the other. Every URL pointing at GitHub must use the repository name: `PROJECT_URL` in `config.py`, `REPO_URL` in `install.sh` and `mailchilla.sh`, and the install commands in both READMEs. GitHub still redirects the old `vogster/Mailchilla`, but only until somebody else claims that name — which would turn the README's `curl … | bash` line into somebody else's script.

Mailchilla: an email bot plus FastAPI web panel that hands out [3x-ui](https://github.com/MHSanaei/3x-ui) VPN subscriptions. A user emails a code word, the bot creates the client in 3x-ui and mails back the subscription link. Commands accepted by mail: the code word (or `/start`), `/status`, `/help`, `/broadcast` (admin address only).

## Commands

```bash
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt -r requirements-dev.txt
cp .env.example .env          # then fill XUI_*, ADMIN_PANEL_USER/PASSWORD/SECRET
python run.py                 # bot thread + web panel on 127.0.0.1:8080
python email_bot.py           # the bot alone, no panel
```

```bash
python -m unittest discover -s tests   # what CI runs
```

There is no linter config and no build step. The tests are unittest, no pytest, and they fall into two kinds. Most are pure: coercion, the code-word matching, the letter texts. `tests/test_panel_routes.py` is the other kind — it drives the panel through `fastapi.testclient` with 3x-ui stubbed out, and exists for one failure in particular: a template reading a context key the route never sent. Jinja resolves that to Undefined in silence, the page still renders, and the missing part is found by somebody clicking a week later. **A new page or a new context key wants a line in that file**; asserting on one string from the page is enough. `httpx` is what `TestClient` needs and lives in `requirements-dev.txt`, so an installation does not carry it.

```bash
python docs/stand.py --lang ru         # a panel on stand-ins, http://127.0.0.1:8099
```

**The test stand is the way to look at a change without a 3x-ui or a mailbox.** `docs/stand.py` copies the tree to the system's temporary directory and starts the panel from the copy, on `docs/stand_panel.py`: a 3x-ui kept in memory and filled from `docs/demo_data.py` (it keeps what is done to it until the stand restarts), and an outbox that is a folder — nothing on the stand is ever sent. `/stand` on it takes a letter "to the bot" and hands it to `email_bot.process_message`, which is how registration, `/status` and `/broadcast` are tried, and lists what was answered. The sign-in is the one `docs/shots.py` uses and is printed at start. What was saved on the stand (settings, tariffs, texts, outbox) survives a restart unless `--fresh`; the code is copied anew each time, so **restart the stand after an edit**. The Mail pages on it read two mailboxes kept in memory (`docs/stand_mail.py`, on `tests/fake_imap.py`), and SMTP is closed off there as well as replaced. `stand_panel.install()` must answer every `XuiClient` method that makes a request — `tests/test_stand.py` fails when one is added and forgotten, and `_request` itself raises on the stand rather than reach a real panel.

Beyond the tests and the stand, verification is by running the process and watching the log (`logs/bot.log`, or the `/logs` page).

**A running panel picks up template edits but not Python ones.** Jinja re-reads a template on every render, while routes, `settings.py` and the rest are already imported — so editing both and reloading the page leaves the new markup running against the old route. The markup then reads context keys the route never sent, Jinja quietly resolves them to Undefined, and the feature disappears instead of erroring. Restart the process after any Python change, and be suspicious of "it renders but the new thing is missing".

**Run a panel you intend to poke at from a copy of the directory, not from the checkout** — which is what `docs/stand.py` does for you, and why its panel half refuses to start beside a `.git` directory. `settings.SETTINGS_PATH` and `email_texts.TEXTS_PATH` are built from each module's own `__file__`, so `os.chdir` does not move them — only running the code from somewhere else does. Copy the tree to a scratch directory and start it there; then a stray save, a wizard step or a reset lands in the copy.

**Anything that exercises saving writes the installation's own files.** `settings.save()`, `email_texts.save()` and `tariffs.save_tariff()` write `settings.json`, `email_texts.json` and `tariffs.json` in the project directory itself — there is no test mode and no fixture path. A throwaway request against `/settings` or `/settings/texts` therefore overwrites a real configuration, and `email_texts.reset()` discards real edits. Run such checks against a copy of the directory, never against a checkout someone is running the panel from.

On an installed server the same work goes through `mailchilla` (`status`, `restart`, `log`, `update`, `passwd`, `totp-off`, `check`). The shell scripts have no tests either; `bash -n install.sh mailchilla.sh` is what CI runs, and the release workflow will not publish a tag that fails it.

## Architecture

**No database.** 3x-ui is the single source of truth for client state; everything is read back from its API on each request. The only local state is `settings.json`, `email_texts.json` and `tariffs.json` (all gitignored — they hold secrets, per-installation text and the words that let people in) plus the in-memory log ring buffer. A tariff is not client state: it is a template read once, at creation, after which the values live on the client in 3x-ui like everything else.

**Two-layer configuration.** `config.py` reads `.env` into module-level attributes. `settings.py` then loads `settings.json` and **writes over those same `config` attributes** (`settings._apply()` does `setattr(config, key, ...)`). So:

- Read a setting as `config.IMAP_SERVER` at call time — never `from config import IMAP_SERVER`, which captures a stale value.
- `.env` only seeds a first run. Anything in `settings.MANAGED_KEYS` belongs to the panel and takes effect live, with no restart.
- `.env` is reserved for what must exist before the panel can start: 3x-ui access, panel login, host/port, logging.
- Adding a panel-editable setting means: a default in `config.py`, the key in `MANAGED_KEYS`, a `_coerce` branch in `settings.py`, and a field in the settings template/route.

**Client identity in 3x-ui is awkward, and the helpers exist for a reason.** The 3x-ui `email` field is an identifier with a restricted character set (`build_client_email` strips the rest); the sender's display name goes into the separate `comment` field (`build_comment`), because gluing `Name <email>` into `email` makes the panel reject the client. Lookups by address scan the whole client list (`XuiClient.find_client_by_email`, via `extract_bare_email`); updates and deletes key off the UUID (`XuiClient.client_key` prefers `uuid`, falls back to the numeric `id`). Clients created by hand in 3x-ui may carry no address at all — code that mails clients must skip rows whose `bare_email` is empty.

`xui_client.get_shared_client()` returns one process-wide `XuiClient`; it holds the login session cookies and re-authenticates on a 401/redirect, so don't construct `XuiClient()` directly.

**Tariffs are what a client gets; codes are how they got in.** `tariffs.py` holds both in `tariffs.json`: a tariff carries a name, traffic, term and inbounds, and a code carries a word, the tariff it opens, whether it is permanent or a one-shot invitation, and whether a letter using it waits for approval. Keeping them apart is what lets a leaked word be revoked without touching the tariff, and lets one tariff have several ways in.

- **Which tariff a client is on lives in 3x-ui, not here.** The client's `group` field is the tariff's *name*; `add_client` sets it in the same request that creates the client (verified against a live panel — the documented `add` body has no such field, but the panel takes it), `update_client` moves a client between groups, and `clients/list` returns `group` on every client, so the panel never pays an extra request for it. `GET clients/groups` also returns per-group client counts and traffic totals, which nothing uses yet.
- **Deleting a tariff leaves its clients' group labels alone**, on purpose: they hold their own limits and a label is not a limit. The labels then name a tariff that does not exist, which the client list marks (a dashed chip) and the tariffs page counts under "Groups without a tariff" — visible rather than lurking. A tariff created again with the same name simply owns them again, which is what a name-keyed group means.
- Because the name is the key, **tariff names must be unique** (`save_tariff` refuses a duplicate) and renaming a tariff must call `XuiClient.rename_group` — `routes_tariffs` and the wizard both do. An empty group is not a row in 3x-ui at all, so renaming one reports failure harmlessly.
- **A tariff may limit devices**, in `limit_hwid` (0 is none, and so is a tariff written before the field existed). It becomes the client's `limitHwid` in 3x-ui, which counts devices by the hardware id an app sends when it fetches the subscription. `add_client` sends the key **only when there is a limit to set**, so a panel from before HWID limits is asked exactly what it always was. Such a panel takes the client and drops the field in silence, which is why whoever creates a client reads it back through `email_bot.kept_device_limit` — it warns in the log and returns what the panel actually holds, and that, not the tariff's figure, is what the letter states. The warning tells two faults apart, because they have different remedies: no field at all is an old panel, while a field holding something else is a creation that failed on one of its inbounds — 3x-ui applies `limitHwid` only when the client went into every inbound asked for. `XuiClient.device_limit()` returns `None` for "the panel does not know the field" and `0` for "no limit": the client card and the edit form offer nothing about devices on `None`. A device stays registered until it is taken off, so the card lists them (`get_client_devices`) and can forget one or all (`forget_client_devices`) — asked only of a client that has a limit, since without one 3x-ui registers nobody. `/status` asks for the same list under the same condition, and `templates._status_devices` decides what the letter says: the count against the limit, the names (`XuiClient.device_label` — a model, or failing that a system; the empty answer is the caller's to word, since the panel and the letters speak different languages), and a line of its own once every slot is taken. `devices=None` there means the panel stated the limit and would not list the devices: the letter then says "up to N" and never "0 of N", which would be a claim nobody checked.
- **The tariff is read once**, in `handle_registration`, and never again. Editing one changes nothing for anybody already registered, and the form says so — do not add code that "re-applies" a tariff.
- **A word is matched whole, and only in what the sender typed.** `email_bot.readable_text` cuts the body at the first quoted line and `contains_word` demands no word character either side. Both exist because the welcome letter carries the word back to everybody who replies to it, and because `START` lives inside `RESTART`. Never go back to `word in text`. `find_words` adds one more rule: a word found only as a piece of a longer word that is itself a code does not count — the boundary lets a hyphen stand inside a word, so `AURORA` was found whole inside `AURORA-FAMILY` and the sender was asked which of the two they meant.
- **Two words in one letter are not guessed at**: the bot replies asking which is meant.
- **Words are unique across tariffs** (`tariffs.word_owner`), or what a letter gets would depend on the order the file happens to be written in.
- **There is no approval queue, on purpose.** A registration happens the moment a letter with a working code arrives; nothing waits for the administrator. It was planned — a `requests.json` of pending applications, a page to approve or refuse them, letters for each outcome — and dropped once codes gained activation limits and a switch of their own: a leaked word now runs out by itself or is put out in one click, and a public word can sit on a deliberately stingy tariff so an unwanted registration costs little. Gotify already pushes on every registration. A `confirm` field existed on codes for this and was removed with the idea. If it comes back, it belongs on the code rather than the tariff, and the queue belongs in a file of ours rather than as disabled clients in 3x-ui — a client disabled by hand and one awaiting approval would otherwise be the same thing.
- **A code is spent after the client exists**, not before: a code burned on a registration that then failed is worse than one used twice. An address that is already a client gets its link again and the code is *not* spent — the invitation stays for the person it was meant for.
- **There is one kind of code, not two.** `uses_left` of `None` is the word handed out openly; a number is how many registrations are left in it, and `1` is what used to be called an invitation. A `kind` field existed briefly and was removed — two fields that can disagree about the same fact are one too many. An old `tariffs.json` carrying `kind` is read fine and simply stops carrying it on the next write.
- **A generated word** (`tariffs.generate_word`) is `secrets.choice` over an alphabet with no `0/O` or `1/I/l`, because it is read off a screen and typed by hand. `enabled` is the switch; switching a code off keeps the record of who came through it, `delete_code` throws it away.
- Words are the identity of a code, so `save_code` takes `was=` to rename one, and carries `used_by` and `used_total` across.
- **Who came in through a code is a count plus a window**, not one growing list: `used_total` is exact forever, `used_by` keeps the last `USED_BY_KEPT` addresses. `tariffs.json` is rewritten whole on every registration, so an unbounded list would make each new client cost a little more than the last. The pages say when the list is only the end of the story, and `code_used_by()` — which the client card uses to name the word somebody arrived by — can only answer within that window.
- `CODEWORD`, `LIMIT_GB`, `EXPIRE_DAYS` and `XUI_INBOUND_IDS` are now only the **seed of the first tariff** — `tariffs.load()` builds it from them when `tariffs.json` is missing. They stay in `settings.MANAGED_KEYS` on purpose, so that a copy rolled back to 0.1.x finds them where it left them. Nothing else reads them.

**Two independent languages.** The panel interface language (`PANEL_LANG`) and the language letters go out in (`MAIL_LANG`) are separate settings.

- Interface: `i18n.t("English string")`, keyed on the English text itself, so English needs no catalogue. `lang/ru.py` is one flat `TEXTS` dict. A key may carry a disambiguating context in trailing brackets — `t("Active [badge]")` — which the catalogue keys on and English strips. New language = `lang/<code>.py` plus an entry in `i18n.LANGS`.
- Letters: `email_texts.py` holds `DEFAULTS_BY_LANG` and the `GROUPS` structure that drives the settings form. Overrides are stored per language in `email_texts.json`, and only strings that actually differ from the default are written. Adding a letter string means adding it to `GROUPS` **and** to every language's defaults.
- A `SWITCH` in `GROUPS` is a `settings.py` key rather than a text — whether a block is sent at all is one setting for the installation, not a string per language — and it carries a fifth tuple element: the fields it governs, drawn inside it as one framed block. Anything that wants the old flat list reads it through `email_texts.walk(group["fields"])`, which yields plain four-tuples.

**In a `.txt` letter template a tag's own line is not a line of the letter.** `trim_blocks` eats the newline after a tag, so a `{% endif %}` standing alone where a blank line used to be removes that blank line — for every letter, whichever way the condition goes. Leave the blank line in after the tag, and assert it in a test: the welcome letter lost the one above its link this way.

**Letters are built twice.** `templates.py` renders `email_templates/<name>.html` and `email_templates/txt/<name>.txt` into an `Email(html, text)` namedtuple; every letter must have both parts. HTML is autoescaped, `.txt` is not. The only markup allowed from editable text is `**bold**` and line breaks, applied by the `emph`/`plain` filters — editable texts are text, not HTML. `t()` inside these templates is `templates.text()` (the letter texts), not `i18n.t()`.

**The bot is three files, not one.** `email_bot.py` had grown to hold how a letter is sent, how the mailbox is read, and what the bot does about what it finds — three jobs that never call each other except at one seam.

- `mailer.py` sends: building the MIME message, SMTP, the Gotify push. It knows nothing about tariffs, commands or clients.
- `inbox.py` reads: the IMAP poll loop, the health of that loop, scanning the mailbox for sender names. `check_mail(handle)` **takes the handler as an argument** rather than importing it — otherwise the loop would depend on the commands, which already depend on the loop's own helpers. It is called `inbox` because the standard library owns `mailbox` and a module of ours beside it would shadow it for the whole process.
- `inbox` also clears the mailbox out, because it is the one place already holding an authenticated connection: when `cleanup_due()` says so, the read letters are moved to the Trash *after* the cycle's letters have been handled, never instead. Only read ones — the flag is set after the handler has finished, so an unread letter is one still owed an answer. The Trash folder is asked of the server (RFC 6154's attribute first, then a list of known names) and no Trash means no cleanup: deleting outright is not the fallback. The schedule survives restarts because the bot writes `MAIL_CLEANUP_LAST_AT` into `settings.json` through `settings.save()` — one of two keys in `WRITE_ON_DEMAND`, which is what keeps it out of the file until it has actually happened.
- **SMTP keeps no copy of a sent letter**, so `mailer.send_email_reply` hands each one to `mailfolders.save_sent_copy` after a successful send. It is a queue and a daemon thread: the worker waits a few seconds (for a provider that files its own copy, and for a broadcast to batch into one connection), then appends to Sent unless a letter with the same Message-ID is already there. Nothing about the copy may fail or slow the send. `send_email_reply` takes `keep_copy=False` for a letter that only exists to be looked at, not answered — the sample sends on the Settings > Letters tab use it, so a preview does not turn up in the panel's Sent folder beside real correspondence. `send_email_via` alone — the settings page's connection test — keeps no copy regardless, since it never goes through `send_email_reply` at all.
- `email_bot.py` is the middle: the commands, the registrations, the letters sent back — and it **re-exports** the transport names (`send_email_reply`, `probe_imap`, `mail_health`, …) so that everything the panel, `run.py` and the tests already call on it keeps resolving, patching included.

**The bot answers people, not machines, and believes a From header only so far.** Three guards, all in `inbox.py` because that is where a letter is first looked at:

- `automatic_reason(msg, from_email)` — `Auto-Submitted`, `Precedence: bulk`, `List-*`, an empty `Return-Path`, a `mailer-daemon`/`noreply` sender. Such a letter is marked read and never reaches the handler. The other half is in `mailer.build_message`, which marks **every** outgoing letter `Auto-Submitted: auto-generated` — so a letter of ours that comes back is refused by the same check. Do not send mail around `build_message`.
- `over_limit` / `note_answered` — ten handled letters an hour per address, then silence. Proven and unproven letters are counted apart, so letters with somebody's address forged into From cannot use up the answers owed to the real owner of it. The count is taken *after* the handler returns: a letter that failed or was put off is seen again next cycle, and counting each sight would throttle somebody for the bot's own trouble.
- `sender_authenticated(msg, from_email)` reads the receiving server's `Authentication-Results` and is passed to the handler as `authenticated=`. **Only `/broadcast` asks for it**: everything else a letter does, it does to its own sender. Only the top-most header counts — anything lower may have arrived with the letter, whatever server it names. No header is no proof, never a pass. **The header is parsed by its grammar, never searched**: the server copies the envelope address into `smtp.mailfrom=` as it stands, and `dmarc=pass@evil.test` is a legal address, as is a quoted one holding spaces and semicolons. `_split_results` and `_PROPERTY` exist for that, a DMARC pass must name this From domain in `header.from`, and any DMARC verdict but pass or none ends the matter. The forgery cases are in `tests/test_inbox_guard.py`; add to them rather than loosening a pattern.

**Letters are fetched with `BODY.PEEK[]`, never `RFC822`.** Fetching a body sets `\Seen` by itself (RFC 3501 §6.4.5), so the old fetch marked every letter read before the handler had seen it — and the whole design of "marked read only once dealt with", the retries and the put-off letters rest on a letter still being unread next cycle. It also matters to the clear-out, which moves read letters to the Trash. `FakeIMAP` in `tests/test_inbox_guard.py` models the implicit flag for this reason.

**`support_watch.py` is the bot looking at Support's mailbox, once a minute, to push a Gotify notification about what is new** — called from the bot loop in `run.py` like the inactivity sweep, on a connection of its own. What counts as new is a mark in `settings.json`, `SUPPORT_NOTIFY_MARK` = `<UIDVALIDITY>:<highest uid>`, one of the `WRITE_ON_DEMAND` keys the bot writes for itself: no mark, or a different UIDVALIDITY, means the mailbox is taken as it stands and nothing in it is announced — otherwise the first look would ring once for every letter of the last year. The mark is written **before** the push and only when it has moved, for the reasons the tests give (`tests/test_support_watch.py`). `mailfolders.arrivals` does the reading and is strictly looking: EXAMINE, headers with PEEK. `UID SEARCH UID n:*` always matches the highest letter there is, even below `n` — the range reads the same either way round — so the result is filtered afterwards. One notification goes out per letter, oldest first, with `SUPPORT_NOTIFY_TITLE` and `SUPPORT_NOTIFY_MESSAGE` rendered through `mailer.render_template` — the same two-field shape and the same safe substitution as the registration push, so a stray brace in a settings field cannot cost a notification, and a brace in a stranger's subject is only a brace. Past `NAMED` letters in one look the rest are counted in a single notification whose wording is fixed and in the panel's language, as is the "(no subject)" a letter without one is given. An untouched title follows the panel's language through `settings._TRANSLATED_DEFAULTS`; the text's default, `{sender}: {subject}`, is the same in every language and is not among them.

**An outage is not an answer.** `XuiClient.find_client_by_email(..., strict=True)` raises `XuiUnavailable` when the client list could not be fetched, where the plain call returns the same `None` as "no such client". The bot's handlers ask strictly — otherwise a registered client is told they are not registered — and the panel's pages do not. `email_bot._handle_letter` turns the exception into `inbox.TryLater`, which the poll loop treats unlike every other exception: the letter stays unread, the attempt is **not** counted towards `MAX_ATTEMPTS`, and the rest of the cycle is skipped. While that lasts `mail_health()["waiting"]` is true and the dashboard says so — the mailbox itself is healthy, so nothing else would. `get_all_clients` returns `[]` for a panel that answers `"obj": null`, because `None` is reserved for "could not ask" and an empty panel would otherwise read as one that is down. A new handler that cannot act for a reason that is not the letter's fault should raise it too.

**The 3x-ui sign-in page is recognised by a redirect, not by the URL.** `XuiClient._landed_on_login` exists because `"login" in response.url` matched every client whose address contains those letters — the address is part of the path. Never test a 3x-ui URL for a substring.

**Entry point.** `run.py` starts the IMAP poll loop in a daemon thread and uvicorn in the main thread, with shared SIGINT/SIGTERM handling (uvicorn's own signal handlers are deliberately disabled). `admin/app.py` also calls `settings.load()`/`email_texts.load()`/`applog.install()` at import, so the panel works when imported on its own; all three are idempotent.

**Panel layout.** `admin/app.py` owns auth and the dashboard and mounts routers from `admin/routes_*.py`. `admin/deps.py` holds the shared Jinja2 environment, globals and `require_auth` — it exists to break an import cycle, so routers import from `deps`, never from `app`. Routes guard with `auth_redirect = require_auth(request); if auth_redirect: return auth_redirect`. `admin/rows.py` flattens a 3x-ui client into the row shape shared by the client list and the broadcast recipient picker.

`mailfolders.py`, behind `admin/routes_mail.py`, is the panel's own view of a mailbox — the Mail page's folders, one letter, its attachments — kept apart from `inbox.py` because it reads for a person to look at rather than for the bot to act on. **Looking must change nothing**: folders are opened with `select(..., readonly=True)` and bodies fetched with `BODY.PEEK[]`, because an unread letter is how the bot knows it owes an answer, and a panel that marked one read by opening it would swallow a registration. `tests/fake_imap.py` records every writable select and unpeeked fetch, and the mail tests assert both lists stay empty; keep it that way when adding a command. **There is exactly one exception, and it is not in the bot's mailbox:** `mailfolders.mark_answered` sets `\Answered` and `\Seen` on a Support letter once a reply to it has gone out — called from the route's background task only after the send succeeded, so a reply that failed marks nothing. Support's mailbox has no bot reading it, and there the strictness only meant a letter answered from the panel went on looking like one nobody had got to. The function refuses the bot's account itself rather than trusting its callers, and it logs out without `CLOSE`: on a folder opened for writing `CLOSE` also expunges whatever somebody else has marked for deletion. The folders are found through `inbox.special_folder` (RFC 6154 attribute first, then names compared after decoding IMAP's modified UTF-7 — the raw name is what goes back to SELECT). An HTML letter goes into a sandboxed iframe as `srcdoc`, with our CSP meta, `<base target=_blank>` and no-referrer placed in front of it by `framed_html`; remote images stay blocked until `?images=1`, and `cid:` images are inlined as data URIs because the frame cannot fetch from the panel. Attachments are served as `application/octet-stream` with `nosniff`, never inline.

- **There are two mailboxes, not one, and `Account` is what tells them apart.** `mailfolders.BOT` reads `config.IMAP_*`/`config.SMTP_*`, `mailfolders.SUPPORT` reads the same shape under a `SUPPORT_` prefix — both live, through a property on each call, never cached on the instance, so a setting saved from the panel applies on the next request. Every function that opens a connection or asks whose address is whose (`_connect`, `list_letters`, `fetch_raw`, `own_addresses`) takes the account as its first argument; `inbox.trash_folder`/`sent_folder`/`special_folder` need none, because they work off an already-open connection and know nothing about credentials. `accounts_available()` is what decides whether the Mail page's account switcher shows Support at all — the bot's mailbox always, Support only once both its IMAP and SMTP halves are set (`Account.configured`).
- **Only Support replies.** The bot's own mailbox stays view-only — `admin/routes_mail.REPLYABLE_ACCOUNTS` is the one place that says so, checked again server-side in the POST route regardless of whether the form is drawn, since hiding a button is not a guard. A reply (`mailfolders.send_reply`) is plain text: `quote_body` appends the original underneath what was typed, `reply_subject` adds "Re:" without doubling one already there, and In-Reply-To/References thread it under the letter it answers — carried from `parse_letter`'s own `message_id`/`references` fields, which exist for exactly this. Sending goes through `mailer.send_email_via`'s `extra_headers` parameter (added for this) rather than through `send_email_reply`, since a reply's identity is Support's, not the bot's, and needs a Message-ID nobody has cached anywhere. Sent like every other letter, fire-and-forget on a `BackgroundTasks` job (`admin/routes_clients.py`'s `_send_welcome`/`_send_personal` are the precedent) — a failure shows up in the log, not on the page.
- **The sent-copy queue now carries an account key.** `save_sent_copy(account_key, message_id, raw)` queues `(account_key, message_id, raw)`; the worker drains a batch that may hold letters from both accounts at once (queued moments apart) and groups it by account before calling `append_copies(account, items)` once per group, so each letter still lands in its own account's Sent folder. `mailer._keep_copy` — the bot's own path — always passes `"bot"`.

**Every letter the Mail pages show was written by a stranger, and they run signed in, in the bot's own process, on a connection to the mailbox the bot reads its work from.** What that has already cost, and the rule each case left behind — the cases themselves are `tests/test_mail_hardening.py`:

- **Nothing typed by anybody reaches IMAP with a control character in it.** `inbox.quote_astring` turns them into spaces, because CR LF inside a quoted string is the end of the command and the start of the next: `/mail/bot?q=a%0D%0AZ1 SELECT INBOX%0D%0AZ2 UID FETCH 1:* BODY[]` opened the Inbox for writing and marked every letter the bot had not answered as read — from a link. Anything new that names a folder, a search term or an id to the server goes through it.
- **Tags a letter may not bring are renamed, not cut out** (`mailfolders._DEFANG`: `<meta` becomes `<x-meta`, `<base` likewise, `<link` until images are asked for). Cutting needs the end of the tag, and both ways of finding it were wrong: "up to the first `>`" stops inside a quoted value, and `[^>]*>` is quadratic on tags that never close — sixty kilobytes of `<link ` held the whole process for three seconds, a megabyte for the afternoon. **Do not write a pattern over a letter's markup that reads "a tag, then anything, then something"**, nor one with two runs and something optional between them — `\s*=\s*["']?\s*` reads like one run and costs the square of it, four seconds for twenty-four thousand spaces, with the interpreter held throughout. One character class per run (`\s*=[\s"']*`), and time anything new on a megabyte of its worst case; `tests/test_mail_hardening.py` has the shape. Anything that holds a document of its own — `iframe`, `frame`, `object`, `embed` — is renamed too: a nested `srcdoc` is a second document the page's care does not reach into. The letter's doctype is recognised by HTML's whitespace, not Python's `\s`: a no-break space in front is text to a browser, and a head put after such a "doctype" lands in the body, where the content policy in it is ignored. `html_to_text` is done by hand in one pass for the same reason as the rest — `html.parser` took forty seconds over forty kilobytes of `<a ` on a Python from before its fix.
- **Sizes a stranger chose are capped where they are used**: `INLINE_MARKUP_LIMIT` on what inline pictures may add to the page (the picture budget counted each once and the page wrote it out once per mention), `HTML_LIMIT` past which a letter is shown as its text, `TEXT_FROM_HTML_LIMIT` on what the standard library's HTML parser is handed.
- **`parse_letter` and `attachment_from` raise `LetterUnreadable`** for a letter nested past what the parser can walk, and every route that calls them answers it with a sentence.
- **A reply is a person writing, and is sent as one.** `mailer.PlainText` is text and nothing else — a bare `str` handed to `build_message` is HTML, which is how the Support reply first went out, its line breaks gone and the quoted letter's markup live — and `automatic=False` leaves off the `Auto-Submitted` header every letter of the bot's carries. The headers a reply is threaded by are rebuilt from message ids alone (`_MESSAGE_ID`), and its subject is one line: both come decoded out of somebody else's letter, and an encoded word decodes to a line break as readily as to anything.
- **The page says where an answer is going.** The client beside a letter is found by `From`, the answer goes to `Reply-To`, and both were written by the same stranger; the address stands beside Send in full, and `reply_elsewhere` puts a warning there when the two differ.
- **Links in the frame are given `rel="noopener noreferrer"` by the page** — on the elements rather than in the markup, since an attribute can be spelt with character references no pattern sees; every `a` and `area` rather than `a[href]`, since an SVG link's address is `xlink:href`; and on a timer as well as on load, which a picture that never finishes arriving puts off for ever. Behind it, `admin/app.py` sends `Cross-Origin-Opener-Policy: same-origin` on every response (`_NoWayBack`), which tells the browser the same thing about whatever the page missed.

`admin/routes_mail.py` is the Mail page and reads the client list once per page to mark who wrote; it opens a fresh IMAP connection per request and stores nothing.

Broadcasts run as in-memory background jobs (`admin/routes_broadcast.py`) because sending takes minutes; the browser gets a self-refreshing status page. Job state dies with the process, by design.

**Dates are a pair of inputs.** `_datefield.html` draws a text box that speaks `дд.мм.гггг` and a hidden input carrying the ISO date; the calendar itself is in `base_admin.html`, keyed off `[data-datefield]`. The hidden half keeps the id, so anything listening for changes keeps working, and the widget dispatches `input` on it when a day is picked. Month and weekday names come from `Intl` in the panel's language, so a new language needs no entries. Without JavaScript the visible box is what gets posted — which is why `_end_of_day()` accepts both shapes.

**State files are written through `statefile.write_json`** — atomically, and with mode 600. `settings.json` holds the mailbox passwords and `tariffs.json` the code words; a plain `open()` takes the process umask, which under systemd left them readable by every account on the server. `run.py` also sets `umask 077` for the log, the generated unit carries `UMask=0077`, and `mailchilla update` re-closes existing files through `lock_state_files`. A new state file goes through the same writer and into `STATE_FILES`.

**The sign-in form is rate-limited in memory** (`LOGIN_ATTEMPTS` per `LOGIN_WINDOW` in `admin/app.py`), keyed by the client address. Behind a proxy or the tunnel that address is always 127.0.0.1, so the limit is shared — which is why it is a ceiling on the rate that lifts by itself rather than a lock: a lasting one would let a stranger keep the administrator out.

**The second step of signing in is three pieces, and the secret has one door.** `totp.py` is RFC 6238 on the standard library and knows nothing of the panel; `admin/twostep.py` is what the panel adds — the ceiling on wrong codes, and the secret that has been shown as a QR code but not yet proved by a code; `admin/routes_totp.py` is the page, `/settings/totp`, which the General tab only links to.

- **There is no switch, only `TOTP_SECRET`**: empty is off (`settings.two_step_on()`). A switch beside a secret would be two fields able to disagree about one fact.
- **`settings.save()` refuses `TOTP_SECRET` outright** (`settings.GUARDED`), whatever value comes with it. The settings form and the Letters tab hand `save()` whatever a request carried — `/settings/texts` saves any `setting:` or `switch:` field — and a session must not be enough to take the second step off or swap the secret for the sender's own. `settings.save_two_step()` is the only writer, and its callers are the page, after it has checked a code, and `mailchilla totp-off`. A new route that saves settings needs no thought about this; a new *writer* of the secret does.
- **The secret is never read back** (`settings.NEVER_REVEALED`): `/settings/secret` and `settings.secret()` refuse it, and it reaches a page exactly once, on the enrolment page, which is sent `Cache-Control: no-store`. Moving to another phone is switching off and setting up again.
- **A code is used up by being right** (`totp.accept` remembers the last counter it said yes to), which is why the sign-in form looks at the code only behind the right password — otherwise a stranger guessing at the password could spend the administrator's code. The same rule is why switching off straight after signing in wants the *next* code.
- **Wrong codes are counted apart from wrong passwords and for everybody at once** (`twostep.CODE_ATTEMPTS` per `CODE_WINDOW`): only somebody who already has the password can run that count out, and they are not held to one address. Like the password's, it lifts by itself. The log line "the password was right and the code was not" is the one that means the password has leaked. **The sign-in form and the switch-off form keep separate counts** — with one between them, an open session posting wrong codes at `/settings/totp/disable` kept every code at `/login` from being looked at — and a right code hands back its own charge without wiping the wrong ones before it, since the count is everybody's.
- **The secret being set up belongs to one session** (`twostep.pending(owner)`, keyed by an id `routes_totp._setup_id` puts in the session — the id, never the secret, since the cookie is signed and not sealed). It was one per process at first, and the second step is switched on above all when the password is thought to have leaked: a second session signed in with that password had only to open the same page to see the secret the administrator's app was about to be given.
- **Both directions take a code.** On: a secret is written only after the app has produced a code from it — `twostep.confirm` — so a QR code that never scanned locks nobody out. Off: `/settings/totp/disable`. The way round is `mailchilla totp-off`, which stops the service first, because the running panel holds the secret in memory and writes all of `settings.json` on its next save.
- **A secret in `settings.json` that is not base32 reads as off, with an error in the log**, rather than as a door no code opens: whoever can spoil that file can empty it.

**A question before a destructive action is a `data-confirm` attribute on the form** (with `data-confirm-danger="1"` for a red button); `base_admin.html` intercepts the submit and shows the panel's own dialog. Never `onsubmit="return confirm({{ …|tojson }})"`: `tojson` puts the text in double quotes inside a double-quoted attribute, the browser reads `return confirm(` as the whole handler, cannot compile it, and submits the form unasked. Deleting a tariff went through without a word for exactly that reason.

**No static files.** All panel CSS and JS is inline in `admin/templates/base_admin.html` (~1.4k lines); there is no `StaticFiles` mount.

**Logging.** `applog.install()` attaches a ring buffer (read by `/logs`) and a rotating file to the root logger. Use `logging.getLogger(__name__)` and log at INFO for anything an admin should see in the panel; per-poll noise goes to DEBUG.

## Installation, releases and the update path

`install.sh` and `mailchilla.sh` live at the repository root; the installer copies the latter to `/usr/local/bin/mailchilla`. Both are bilingual.

**Both need bash 4.0+** — `declare -A` for the message tables and `${var,,}` for the answer comparisons. Every supported distribution has it (CentOS 7 is already on 4.2); bash 3.2 in practice means macOS, where these scripts cannot run anyway. The version guard sits at the very top of each file, above the first `declare -A` and above `set -o pipefail`, and is deliberately written without arrays, `[[ ]]` or `set -o` so that a non-bash shell also reaches it. **Do not move it into a function** — the table is built as the file is read, so a check called from `main` never runs.

**Strings in the scripts follow the same rule as `i18n.py`.** One `declare -A MSG` table keyed `lang.key`, and `t key [args]` falls back to English when a key is missing in the other language, so a partial translation is safe. `{0}`, `{1}` are the placeholders. When adding a string, add both languages — the key balance is easy to check:

```bash
grep -c '^\[ru\.' mailchilla.sh && grep -c '^\[en\.' mailchilla.sh
```

**Versions are tags, never a branch.** `install.sh` checks out the newest `v*` tag (falling back to `origin/main` only when the repository carries no tags); `mailchilla update` finds the latest with `git ls-remote --tags`, so no GitHub API and no rate limit is involved. A GitHub Release is cosmetic — nothing breaks if one is forgotten.

Cutting a release means: bump `APP_VERSION` in `config.py`, write the section in `CHANGELOG.md`, commit, tag `vX.Y.Z`, push. `.github/workflows/release.yml` refuses a tag that disagrees with `APP_VERSION` — the version is displayed in the panel sidebar, so a mismatch is visible to every user. `mailchilla update` shows that same CHANGELOG section before asking for confirmation, so each entry should read as something a person wants to know before updating.

**Four files are the installation, and nothing may clobber them:** `.env`, `settings.json`, `email_texts.json`, `tariffs.json`. They are gitignored, which is exactly why the update is `git checkout` rather than unpacking a tarball — ignored files are left alone. `mailchilla update` still copies all of them to `/opt/mailchilla-backups/<date>/` first and restores them if the panel fails to answer after the restart — the list is `STATE_FILES` in `mailchilla.sh`, and a new state file that is not added to it is lost on the first update.

No migration step exists, and none is needed: a key absent from `settings.json` falls through to `BASE[key]` in `settings._apply()`, and `email_texts.json` stores only strings that differ from the shipped default. A *downgrade* is the lossy direction — `settings.load()` warns about unknown keys and drops them on the next save, which is what the backup is for.

Other things worth knowing before editing these scripts:

- **Liveness is an HTTP request, not `systemctl is-active`.** With `Restart=always` a service crash-looping reads as active. `wait_for_panel` polls `http://127.0.0.1:$PORT/login`.
- **The menu appears only on a tty.** `mailchilla` with no arguments and no terminal prints `status` instead of hanging on a prompt in cron or a pipe.
- **Values never go into an unquoted heredoc.** `.env` is written with `printf '%s'` per line, because a password is arbitrary text and a backtick in a heredoc would execute. In the file itself values are single-quoted so python-dotenv does not expand a `$`. `env_set` in `mailchilla.sh` keeps the same convention.
- The generated systemd unit deliberately does not use `EnvironmentFile`, for the reason `README.md` gives.
- **Every git call against the install directory needs `safe.directory`.** The repository belongs to the `mailchilla` service user while the command runs as root, and git otherwise refuses with "detected dubious ownership" — which silently breaks the version display and the whole update path. `install.sh` adds a system-wide exception and `mailchilla.sh` routes every call through its `git_repo()` wrapper; do not reintroduce a bare `git -C "$INSTALL_DIR"`.
- `/etc/mailchilla/install.conf` holds the state of the installation — directory, script language, service and user names. It is not application configuration and the app never reads it.

## The 3x-ui API

`3xui-docs/` (gitignored, not part of the project) holds the reference for the panel this talks to: `3xui-api-docs.md` — 116 endpoints, prose and example payloads — and `3xui-api-reference.json`, the same as a machine-readable collection. Read it before guessing at a request shape; it is the only description of the remote side available offline.

Two things about it are worth knowing without opening it:

**This is the newer, client-first API.** Clients have top-level endpoints — `/panel/api/clients/add`, `/update/:email`, `/del/:email`, `/:email/attach`, `/:email/detach` — rather than the classic inbound-scoped `/panel/api/inbounds/addClient` with a JSON-encoded `settings` string. A client is created once and attached to several inbounds by id in the same call, which is why `XuiClient.add_client` takes an `inbound_ids` list. Anything written against the old 3x-ui API, including most examples found online, will not match.

**`update/:email` replaces the row, it does not patch it.** Every field to be kept must be sent back — that is what `XuiClient._normalize_update_payload` is for, and why updates read the client object first.

Endpoints this project actually calls: `/login`; `clients/add`, `clients/list`, `clients/get/:email`, `clients/update/:email`, `clients/del/:email`, `clients/:email/attach|detach`, `clients/onlines`, `clients/lastOnline`, `clients/links/:email`, `clients/traffic/:email`, `clients/groups/rename`, `clients/hwids/:email` (POST lists the devices, DELETE forgets them all, DELETE `…/:id` forgets one); `inbounds/list/slim`; `server/status`. The group payloads are `{"name": …}` for create and delete, `{"oldName": …, "newName": …}` for rename, `{"emails": [...], "group": …}` for bulkAdd. The docs describe much more — bulk operations, client groups, subscription links by `subId`, Xray control, per-metric history — none of which is wired up yet.

Notes that matter when reading responses: everything comes back as `{"success": bool, "msg": str, "obj": ...}`. `inbounds/list/slim` strips `settings.clients[]` down to `{email, enable, comment}` and omits uuid/subId, so it is only good for listing inbounds — per-client detail needs `clients/list` or `inbounds/get/:id`. Times are milliseconds since the epoch, traffic is bytes, and `totalGB` is bytes too despite the name. Auth works either by session cookie from `POST /login` (with `X-CSRF-Token` from `GET /csrf-token` on unsafe methods) or by `Authorization: Bearer <token>`, which skips CSRF entirely. `XuiClient` sets the bearer header at construction when `XUI_API_TOKEN` is set and short-circuits `login()`; without a token it signs in for a cookie and retries once on a 401/403 or a redirect to the login page.

**`login()` is not a connectivity check.** With a token set it returns `True` immediately without making a request, so it reports success against a wrong token, a dead host or a typo in `XUI_URL`. Anything meaning to verify that 3x-ui is actually usable must issue a real request — `mailchilla check` asks for `inbounds/list/slim` for exactly this reason, and calling `login()` there was a bug. It never sends a CSRF header on either path — so if a panel starts enforcing CSRF on cookie sessions, the token is the working route and that is the code to fix.

## Conventions

- Comments in this codebase explain *why*, often at length, and frequently record a bug that motivated the current shape. Match that when touching the same code; don't strip such comments when refactoring.
- Secrets (`IMAP_PASSWORD`, `SMTP_PASSWORD`, `GOTIFY_TOKEN`) never reach page markup: forms post back `settings.UNCHANGED` when untouched, and the real value is fetched separately by `/settings/secret`.
- User-visible strings in panel templates and Python go through `i18n.t()`; letter strings go through the editable-texts layer instead of being hardcoded.
- **The Russian catalogue is kept complete.** The captions and hints in `email_texts.GROUPS` are interface strings and need an entry in `lang/ru.py` — adding a field without one leaves English text sitting in a Russian panel. One pass over `GROUPS` finds every gap:

```bash
python -c "import email_texts;from lang.ru import TEXTS;print([s for g in email_texts.GROUPS for f in g['fields'] for s in (f[1],f[3]) if s and s not in TEXTS])"
```
- `README.md` and `README.ru.md` are parallel — a user-facing change belongs in both, and their section structure is kept identical.
- A user-visible change also belongs in `CHANGELOG.md` under `## [Unreleased]`, since that text is what `mailchilla update` shows people.
